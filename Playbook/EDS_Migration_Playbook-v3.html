Section 1.1 · Adobe Skills for EDS Migration

Adobe Platform Skills — What They Are & How They Work

Adobe ships a curated set of skills for Edge Delivery Services under the aem-edge-delivery-services plugin, with content-operations skills in the companion aem-edge-delivery-services-content-ops plugin. These skills are versioned instruction sets that run inside Claude Code, Cursor, GitHub Copilot or any AI-assisted development agent. Each skill encodes a repeatable migration procedure — page scraping, structure analysis, block mapping, import generation, preview — executed by the agent on real source pages and the real target project, not invented per engagement.

The anatomy of an Adobe skill in a migration project

What it is
A versioned markdown file (SKILL.md) inside the plugin. The skill tells the AI agent exactly what to produce, what rules to apply and what to refuse — specific to EDS conventions (sections, blocks, default content, document-based authoring).
How it runs
Invoked by name or by intent in the coding agent — e.g. “import this page: <URL>” triggers page-import, which orchestrates its sub-skills. Migration skills work on real source URLs and the real target block inventory — not on hypothetical content.
What it covers
Adobe skills address content migration (scrape, decompose, map to blocks, generate import HTML, preview) and post-import operations (block testing, preview-vs-live diff, bulk metadata audit). Asset transfer, visual regression and brand checks are outside the skill layer.
Installation
Install at Project scope so every engineer and CI agent runs the same version throughout the migration (see Section 1.2). Commit the project context files (AGENTS.md, INSTRUCTIONS.md) to Git before Phase 0 ends.
The one rule that makes migration skills work: if a migration constraint is not in AGENTS.md, INSTRUCTIONS.md, a skill file or the approved mapping files, no agent will honour it. The authoring model, the component-to-block mapping, URL and redirect rules, and excluded paths must all be machine-readable before any agent touches a source page.
Section 1.2 · Setup

Installing Adobe Skills — Prerequisites & Bootstrap

All Adobe EDS migration skills are distributed as plugins from the adobe/skills repository. Install once at project inception; skills version-lock together so the whole team and CI agents run identically.

Bootstrap sequence — run once before Phase 0 migration work begins

Step 1 · Install the plugins
Install the aem-edge-delivery-services and aem-edge-delivery-services-content-ops plugins using the instructions for your AI coding tool at github.com/adobe/skills. The page lists the install commands for each supported tool, so developers use the commands that match the tool the project has standardised on.

Install at Project scope. Verify the skill list in the agent before Phase 0 ends — page-import, scrape-webpage, snowflake, content-modeling, content-diff and the others in Section 1.4 must all appear.
Step 2 · Establish project context
Confirm AGENTS.md (shipped with the EDS boilerplate) is present, then create INSTRUCTIONS.md recording the authoring model, mapping-matrix location, URL rules and excluded paths. These files are consumed by every migration skill as project ground truth. Instruct agents to “search www.aem.live” for documented patterns.
Prerequisite — EDS project in Git
Target EDS repository exists (from the boilerplate or an existing project) with the AEM Code Sync GitHub app installed. If it has not been set up, use the optional create-site skill (DA.live projects) — Section 1.4, Phase 0. The repository should have the content source connected (SharePoint / Google Drive, DA.live or AEM Author for UE). Node.js and the AEM CLI available for local preview with aem up.
Prerequisite — access & source
Read access to every in-scope source URL (and authenticated preview where required). Client approval recorded for any agent processing client content.
Adobe reference: for authoritative setup guidance see github.com/adobe/skills and aem.live documentation.

Section 2.1 — AI-First Agentic Layer

ABG Agent Suite — Agent Overview

The ABG agent suite is the AI-first agent layer for Website-to-EDS migration, with one agent per migration object type. Each agent has a precise scope. They are not interchangeable, and they complement Adobe's EDS skills (Tab 01) and Adobe's Experience Modernization Agent (Section 2.4). For which route to use, and what each costs, see Section 2.5.

The boundary that must be stated in every SOW: Adobe EDS skills and the Experience Modernization Agent scrape, map and import pages into EDS block structure. The ABG agent suite covers component mapping at scale, visual parity and brand compliance, and provides the fallback content-conversion route. Conflating the two is the most common scoping error in EDS migration engagements.

Section 2.3

ABG Agent Specifications

Specification for each agent in the ABG suite — inputs, outputs, constraints and EDS boundary.

CONTENTContent Migration Agent (ICM)
EMA recommendedUE authoring only
Authoring model support: the Content Migration Agent supports migration to EDS with Universal Editor (UE) authoring only. It is not applicable to Document-Based Authoring (SharePoint / Google Drive) or DA.live projects — use the Experience Modernization Agent or Adobe EDS skills for those.
Cost: for EDS with Universal Editor, the only running cost is the client’s LLM subscription. Accenture does not bear this cost. This makes it the lower-cost option for UE migrations where EMA does not fit the budget (Section 2.5).
Consistency at scale: it runs on a fixed, customised set of mapping rules rather than open-ended prompting, so the same source pattern always produces the same output. This makes results predictable and repeatable, and it is recommended for migrations with a high number of pages.

An independent agentic application. Given the URL of a source page, it scrapes and chunks the HTML into logical DOM sections, uses Retrieval-Augmented Generation (RAG) against a vector database of component metadata to find the best-fitting target for each chunk, and synthesises the migrated page via a GenAI builder. For EDS, the target is an approved EDS block or default content, produced as Universal Editor content.

Solution Architecture — 3-Phase Pipeline

1. Extraction Engine (Source Analysis)
  • Source ingestion: URL of the source page to be migrated
  • Scraping & chunking: HTML scraper fetches raw HTML and associated assets
  • DOM identification: identifies logical DOM chunks — headers, feature sections, footers
2. Semantic Intelligence (Vector & AI Bridge)
  • Vector DB: stores target block metadata — semantic descriptions, block table structures, allowed fields
  • AI mapping & RAG: finds the best functional match for each extracted chunk
  • No match: logged as a migration exception — never auto-generated as a new block
3. Generation (EDS Construction)
  • Content synthesis: GenAI builder fills block / default-content structures with extracted content and asset references
  • UE output: produces Universal Editor–compatible content (UE projects only)
  • Preview, not publish: pages land in preview for comparison; never auto-published
Inputs
  • Approved page list from the Gate G1 scope record
  • Source page URL (scraped directly from the source site)
  • Vector DB of target EDS block metadata
  • Approved component-to-block mapping (Gate G2)
Outputs
  • Import-ready EDS page content (reviewed before preview)
  • Per-page conversion log: mapped, skipped, flagged for manual review
  • Conversion error report: sections with no mapping rule
  • Content diff report: source vs converted page
Constraints
  • Pilot pages first (G3) before bulk waves
  • Unmapped sections logged as exceptions — never silently dropped
  • Client approval and data-residency assessment before use
MAPPERBlock Mapper Agent
Note: the Block Mapper Agent is used internally by the Content Migration Agent (ICM) to map source components to existing blocks; it can also be run on its own during content mapping.
Scope: the Block Mapper Agent only maps to existing blocks developed by the development team. It does not create new blocks. Where no existing block fits, the source block is logged as an unmapped exception for the Migration Architect.

Semantic search across the target project's existing EDS block library to find the best existing match for each legacy component being migrated. Prevents unnecessary block builds — the most common source of cost overrun in migration projects.

Inputs
  • Legacy component inventory (from Phase 1)
  • Existing block library developed by the development team
Outputs
  • Mapping report: per-block verdict (default content / existing block / existing block variant / unmapped)
  • Mapped path: existing block + content-model notes
  • Unmapped list: blocks with no match, raised as migration exceptions — no new block is generated
  • Updated mapping matrix (reviewed by architect at G2)
Constraints
  • Prefer default content over a block wherever an author could create it in a document
  • Maps only to existing blocks — never creates or scaffolds new blocks
VISUALVisual Comparison Agent
Gate G4 — blocking

Adobe ships no equivalent visual regression tooling for EDS migration — this is the definitive visual regression tool for the project. Captures screenshots of target pages on both the source site and EDS preview, diffs them pixel-by-pixel and classifies each page as Pass / Regression / Acceptable Drift. Required gate artefact before Gate G4 sign-off.

Inputs
  • Source URL list (top 50+ critical pages minimum)
  • EDS preview URL list (same pages)
  • Approved design baselines (redesign only — replaces source as reference)
  • Acceptable drift threshold (default: >95% pixel similarity for as-is)
  • Viewport configurations (desktop, tablet, mobile)
Outputs
  • Per-page classification: Pass / Regression / Acceptable Drift
  • Side-by-side screenshot diff for all regressions
  • Aggregate report: pass %, regression count, drift count
  • Blocker list: pages with a Regression verdict
  • Exported report for the Gate G4 evidence pack
Constraints
  • Add auth handling where EDS preview is protected
  • Stabilise dynamic content before capture
  • Every diff explicitly accepted or rejected by a named QA professional — never auto-approved
BRANDBrand Readiness Agent

Validates migrated content on EDS preview and live against the client's brand guidelines. For migration, the primary risk is that content authored on the source site — sometimes over many years, under different brand guidelines — arrives on EDS in a state that violates current brand standards. Bulk import also introduces conversion errors that spell-check and image-relevance checks catch. This agent surfaces those issues before business owners sign off at Gate G4. Where Adobe's Governance Agent is licensed, do not run both as the gating check.

Inputs
  • EDS preview page list (post-import)
  • Brand guidelines (logo usage, colour, tone of voice)
  • Design token set (as-is carries forward existing; redesign uses new tokens)
  • Image library (for image-relevance scoring)
Outputs (tiered report)
  • Blocker: must be fixed before Gate G4 (wrong logo, critical colour violation)
  • Warning: recommended, not blocking (tone deviations, outdated imagery)
  • Pass: compliant content
  • Summary count per tier; page-level drill-down
  • Remediation suggestions per finding
Constraints
  • Findings require human triage
  • Review only migrated content and approved exception blocks
  • Continues as a steady-state guardrail during hypercare
Section 2.4 — Adobe Agent · Primary migration route

Experience Modernization Agent (EMA)

§3Content Inventory
§3.1URL list & inventory sheet

The client provides the in-scope URL list or a reference XML sitemap. This is the single source for the inventory — the team does not build the list from other sources. Confirm with the client that the list covers PDFs and downloads, locales and any pages not in the sitemap.

Skills: scrape-webpage, identify-page-structure — Tab 01 · Phase 1; agent: EMA web scraping — Tab 02 · Section 2.2.

§3.2Disposition per page (ROT)

Decide per page: migrate, rewrite, merge or retire. Retire what is redundant, outdated or trivial (ROT). Retired URLs still need a redirect if they carry traffic or backlinks.

🛠 A noticeable share of source pages can usually be retired. Each retired page is one less to import, validate and maintain — push for the decision early with content owners.

§3.3Group pages into templates

Cluster pages by structure, not URL path: home, landing, article, product / detail, listing, form, legal. A handful of templates usually covers the large majority of pages. Pilot one representative page per template first (§2.5, §6.5).

§3.4Separate applications from content

Flag pages that are really applications — search results, login / account, calculators, configurators, checkout, store locators. These go to §7 (Integrations), not §6.

§3.5Target URL rules

EDS document names are normalised to lowercase a-z, 0-9 and -; the full path should stay under 900 characters. Paths such as /About_Us.aspx will change — every change needs a redirect. Decide early whether to keep .html extensions; EDS serves extension-less pages, so keeping old .html URLs means a redirect per page.

Universal Editor (UE): public URLs come from AEM page names and the path mapping in paths.json (e.g. /content/site/en/ → /en/). Agree the mapping here and record it in INSTRUCTIONS.md.

📘 Limits — document naming · Translation and localization · Large sites

§3.6Content ownership, freeze & delta

Define author ownership, migration waves and change tracking. For active sites, plan either a short content freeze on the source before cutover or a delta import of pages changed after the main import (track lastModified from the source CMS). Freeze length and notice period are engagement decisions.

§4Block Mapping
§4.1Mapping order of preference

For every component on the templates, pick the first option that works:

  1. Default content — headings, text, lists, images, links, buttons. No block needed.
  2. Section style (section metadata) — background colours, narrow width, centred text.
  3. Existing block or variant from the project or the Block Collection.
  4. Auto-block — created in scripts.js from a content pattern (e.g. a video link becomes an embed).
  5. Fragment — reusable content (nav, footer, shared banners).
  6. Metadata — page-level data (tags, template, dates).
  7. New block — only when none of the above works, raised as a migration exception.

Skills: authoring-analysis, block-inventory, block-collection-and-party — Tab 01 · Phase 2. Agent: Block Mapper Agent maps to existing blocks only — Tab 02 · Section 2.3.

Universal Editor (UE): section styles, page metadata and fragments are set through component model fields (section model, page properties, fragment component), not tables. Content created by auto-blocking cannot be edited in Universal Editor — use an explicit block where authors need to edit it.

§4.2Content modelling rules

All authoring models:

  • Design what the author sees first; write the code second.
  • Keep block structures shallow: no merged cells, no nested tables, ideally ≤ 2 columns.
  • If two components share most of their structure, make them variants of one block (cards (feature)), not two blocks.

Universal Editor (UE) projects — content is stored in AEM and edited through component models, so the rules above apply to the model as well as the rendered table:

  • Each block needs a component definition, a component model (the fields authors edit) and a filter (which blocks are allowed in a section or container). Skill: ue-component-model — Tab 01 · Phase 2.
  • Keep models shallow; use a container block with child items for repeating content (cards, tabs, accordion items) instead of many numbered fields.
  • Expose variants as a style / classes field on the model rather than as separate blocks.
  • Field names must match what the block JavaScript reads. Test each block by editing it in Universal Editor, not only by previewing imported content.
  • Start from the xwalk boilerplate, which ships the model files (§2.1), and budget the extra modelling effort per block.

  1. Pilot one page per template → review with authors → fix the model, not the page.
  2. Freeze the content model (§4).
  3. Bulk import template by template.
  4. Validate (§9 content checks) — automated diff of source vs result.
  5. Preview / publish in bulk via the Admin API.
  6. Hand over to authors — from this moment, the page is owned by authors.

Universal Editor (UE): imported content goes into AEM, and preview / publish run through AEM (Quick Publish or Manage Publication), not the Admin API.

§6.3Import script rules
  • Detect blocks from the DOM, not from the URL or page position. A new page with an unseen combination of components must still import correctly.
  • Order matters: container blocks before children; specific variants before generic ones; skip elements already inside a matched block.
  • Derive section styles from source CSS classes, not from a per-page list.
  • Rewrite internal links to relative target paths; strip tracking parameters; convert legacy URLs to the new pattern (§3.5).
  • Keep import scripts in the repo (tools/importer/) and exclude them from delivery with .hlxignore.

Universal Editor (UE): internal links stay as AEM content paths (e.g. /content/site/en/page); EDS maps them to public URLs through paths.json (§3.5). Do not rewrite them to public URLs in the import.

§6.4Links, metadata & SEO

Map metadata explicitly: title, description, og:image, canonical, tags, dates, language alternates. Audit source-to-target URLs and ensure no orphan pages. Skill: bulk-metadata — Tab 01 · Phase 5.

§6.6Lessons from real imports
  • Re-importing overwrites manual edits. Once authors touch a page, it is never re-imported — fixes are made by hand or a targeted script.
  • Use full page URLs (/index.html, not /) in import URL lists; some tooling fails on bare domains.
  • Nav and footer are fragments — migrate them separately, early and once.
  • Bulk preview / publish is rate-limited (a resource can be previewed at most once per second). Throttle scripts and retry on 429 / 503.

Universal Editor (UE): the rate limit applies to Admin API scripts. Bulk publishing for UE projects runs through AEM publishing (§6.2).

§7.2Applications & server-side functionality

Applications flagged in §3.4 usually stay on their existing platform behind the same domain via CDN routing, or are rebuilt as blocks calling APIs — decide one by one. EDS blocks do not execute server-side code (servlets, OSGi services, workflows). Secrets never go in block code — anything calling an API with a key needs a serverless / edge function in between.

§7.3Integration field notes

Three lessons from real migrations:

  • The tag manager slows the page. Over the years, sites collect old, unused tags in GTM or Adobe Launch. On EDS these scripts load after the page, but too many of them still lower Lighthouse scores. Audit the tag manager and remove dead tags before migrating.
  • Analytics numbers will change. EDS loads pages in three phases: eager (first section), lazy (rest of the page) and delayed (delayed.js, about 3 seconds after load in the boilerplate). Analytics and the tag manager load in the delayed phase, whereas most legacy sites load them immediately in the <head>. As a result:
    • Visitors who leave within the first seconds are no longer counted, so page views drop.
    • Bounce rate and engagement time shift, because the quickest bounces are not recorded.
    • Some bot traffic previously counted as visits disappears.
    • UTM or referrer data can be lost if the visitor moves to another page before the script loads.
    This does not mean users behave differently. Brief the analytics team before go-live so the shift is not reported as a problem. Business numbers (orders, form submissions) happen after the script has loaded and should stay flat — if they drop, treat it as a tagging or form defect. Tags that must fire early (consent, A/B tests that change what the visitor sees) can be loaded earlier on purpose, at a cost to performance.
  • Forms need their own plan. Each form has a target system, validation rules and spam protection. List every form and estimate the work separately, not as part of page migration.

§10.2DNS, CDN & redirect rules
  • Redirects: explicit one-to-one entries based on real usage data; avoid wildcards (they create 301 → 404 chains). Up to 100k per site. Redirects take precedence over pages — remove stale entries.
  • Do not change content source or code location after final QA.
  • Always point production at main.
  • CDN adds performance risk: re-run PageSpeed on the production domain after cutover (HTTP/1.1, poor origin caching and injected bot scripts are common culprits).
  • Do not block crawlers on aem.page / aem.live — they are already hidden from search engines. Use noindex, not Disallow, to de-index.
  • Schedule go-live early in the week, early in the day, never before a holiday or campaign.
§10.3Post-cutover smoke tests

Immediately after cutover, check priority pages, 404 / redirect behaviour, assets, forms, consent, analytics, navigation, mobile rendering and the publishing workflow. Re-run the Visual Comparison Agent on priority live URLs — Tab 02 · Section 2.3.

§10.4Rollback

Rollback = switch DNS / CDN origin back to the legacy platform. It only works if the legacy site is still running (read-only, on an internal hostname), DNS TTL is low, and content changes made after cutover are tracked for replay.

§10.5Hypercare & exit

Monitor 404s, Search Console, OpTel and analytics daily during hypercare; hold a post-launch review at hypercare exit. Keep the legacy site read-only and reachable for a few weeks. Brand Readiness Agent continues as a steady-state guardrail — Tab 02 · Section 2.3.
